# Findings and Decisions: AttackContext Refactor

## Scope
- Project: Forge 1.20.1 / Forge 47.4.9 / Java 17.
- Target subsystem: `AttackContext`, attack construction, `AttackPattern`, `AttackPipeline`, Bullet/Laser/Brimstone/CSection behavior, and trigger snapshot boundaries.
- User explicitly does not require restoring deleted historical tests as a separate task, but new focused tests are part of final verification.

## Confirmed Current Design
- `AttackPipeline` currently has four modes: `FULL`, `GROUP_AND_BULLET`, `BULLET_ONLY`, and `RAW`.
- `FULL` sends before, plan, and per-context preparation events; `GROUP_AND_BULLET` skips before; `BULLET_ONLY` prepares supplied contexts; `RAW` executes supplied contexts directly.
- `AttackPlan.freezeContexts()` freezes the list, not the mutable `AttackContext` objects inside it.
- `AttackContext` currently mixes owner/shooter, spawn data, rotation and offsets, damage/range/speed, trigger/trajectory data, split sequence, exact spawn behavior, and Brimstone sequence state.
- `AttackContext` constructors copy the trigger and trajectory map, and `copy()` also copies split sequence. Parent/child trigger aliasing has already been addressed by trigger copying.
- `getDamage()` lazily reads owner attack damage if no explicit damage was supplied.
- Invalid range/speed setters silently keep the previous value; construction can therefore leave `bulletRange` at zero.
- `setXRot`/`setYRot` modify the base angle while getters add offsets. Reusing `getYRot()` as input to `setYRot()` can double-apply offsets.
- `BulletAttack` uses yaw offsets for spread. `TheWizAttackPlan` uses `setYRot` for group rotation. Brimstone and ShoopDaWhoop update rotation while scheduled.
- Brimstone currently reuses and mutates one Context while scheduled, including position, direction, and sequence index.
- Brimstone and CSection manually publish `BeforePerformAttackEvent` before invoking a `GROUP_AND_BULLET` request, suggesting migration residue from the pre-pipeline path.
- `LaserProjectile` already owns substantial laser runtime state and is the correct place for `sequenceIndex`.

## User Decisions
- Brimstone should become Pattern-driven while still following the current shooter direction.
- Creating a fresh context (or small context queue) for each Brimstone firing step is considered acceptable; prefer per-step creation so direction is sampled at firing time.
- Builder style is preferred for context construction.
- `attackSequenceIndex` should be removed from generic `AttackContext` and stored in the runtime laser object or Brimstone-specific runtime descriptor.

### Sequence propagation follow-up
- The normal Brimstone scheduler can keep a local counter and write the current value directly to each `LaserProjectile`.
- One Context represents one complete 13-shot Brimstone main axis. The scheduler creates a fresh builder-derived shot Context for every callback and never mutates that base Context.
- Exact-spawn Brimstone split children cannot use `0`: it makes `LaserProjectile.getSourceType()` report `LASER`, breaking Brimstone-only split checks. `SplitExecutor` instead detects a Brimstone child generated by a runtime `LaserProjectile` and calls `BrimstoneAttack.shootSingle(childContext, parentLaser.getAttackSequenceIndex())` directly.
- `shootSingle` is the common no-schedule, no-pipeline path for both scheduled Brimstone shots and split children. This preserves runtime-only sequence state without a descriptor, request metadata, or a generic `AttackContext` field.
- Damage and other attack attributes should be resolved when the Context is created.
- Invalid range/speed must be sanitized safely rather than causing exceptions or game crashes, but the resulting Context must never contain invalid values.
- CompositeTrigger exposure may be intentional. Preserve needed external reads/modifications initially, then explicitly define when mutation is legal and when the execution snapshot becomes read-only.
- Deleted historical tests are out of scope for this review record; new focused tests remain required before claiming completion.

## Design Direction

```text
AttackContext.Builder -> immutable creation-time context snapshot
AttackPattern          -> contexts from a main axis and per-shot geometry
AttackPlan             -> pre-execution group replacement/append operations
AttackPipeline         -> event ordering, cancellation, and execution policy
AttackType             -> conversion of a determined Context into attack objects
LaserProjectile        -> runtime state, including Brimstone sequenceIndex
```

### Builder
The builder/factory centralizes common values (owner, shooter, color, trajectories, trigger, position, direction, damage, range, speed) while retaining explicit attack-specific overrides. It is not intended to hide required parameters; it prevents each attack type from independently resolving defaults.

### Pattern
Patterns should generate new contexts rather than mutate an existing context. Ordinary bullet spread, Wiz rotation, ring/semicircle attacks, and Brimstone should use a main axis plus geometric modifiers.

### Brimstone
At each scheduled firing step, sample the current shooter direction, build a fresh seed/context, invoke the Brimstone Pattern, execute the resulting contexts, and store any sequence number only in the laser runtime object. Do not pre-create a long-lived mutable Context queue unless a later performance measurement justifies it.

### Pipeline
After Context and Pattern contracts stabilize, remove manual before-event dispatch from special attack types if it is confirmed redundant. Then make sound/cancellation ownership and mode semantics explicit and tested.

## V2 Implementation Notes
- AttackPatternContext now uses main-axis terminology.
- AttackContext.copy() is a pure snapshot clone, while Builder remains the creation path.
- Bullet, Laser, and Wiz now share the same main-axis pattern model; Brimstone remains on the V1 runtime path.

## V3 Implementation Notes
- Brimstone now uses a dedicated sequence helper for its 13-shot schedule rather than inlining the shot snapshot logic inside BrimstoneAttack.
- Brimstone shot contexts are derived from AttackContext.copy() and then patched with the current spawn position and, when controllable, the current shooter rotation.
- The helper keeps the 13-shot count explicit and preserves spread offsets on the copied context.

## Risks to Recheck During Implementation
- Trigger copying may be correct for parent/child isolation but too expensive if deep module graphs grow; measure before optimizing.
- `AttackContext` trigger mutation during preparation must not leak into already-created runtime objects.
- Pattern generation must preserve existing spawn positions, spread angles, trajectories, and special attack behavior.
- Brimstone direction tracking must sample the intended entity (`shooter` versus `owner`) consistently.
- Removing rotation setters before all callers migrate could break delayed or special attacks.

## V4 Implementation Notes
- Brimstone now reuses one working context across the 13 scheduled emissions instead of allocating a fresh snapshot per shot.
- The standalone BrimstonePattern helper was removed; its spawn-position and per-shot patch logic now live inside BrimstoneAttack.
- Brimstone shot execution remains sequence-indexed at runtime only, with shootSingle as the low-level entrypoint.
