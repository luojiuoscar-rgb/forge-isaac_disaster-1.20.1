# TearBullet Position Jump Findings

## Evidence Log

- Initial source search found `TearBullet` movement in `entity/custom/TearBullet.java`, trajectory implementations in `registries/trajectory/BuiltinTrajectory.java`, and a shared trajectory consumer in `registries/attack_type/impl/LaserAttack.java`.
- The repository is Forge 1.20.1 and currently has unrelated uncommitted changes; source diagnosis must remain read-only.
- OCR workspace preview found 35 reviewable code files, but none changes `TearBullet`, `BuiltinTrajectory`, the attack pipeline, or any trajectory registry class. The current diff is predominantly the freeze/effect system; only `networking/EntityVisualStateSync.java` is plausibly adjacent and needs an explicit exclusion check.
- OCR usage notes: the installed CLI supports the delegate workflow but emits Markdown rather than the documented JSON flags. `ocr.ps1` is blocked by execution policy; `ocr.cmd` works. `--format` and `-f` are unsupported by this installed version, so preview ran with its default output.
- `BulletAttack.createBullet` sets the spawn position to an offset point, stores the preflight origin, sets the initial velocity, and sets `deltaMovement` to that same velocity before `addFreshEntity`.
- `TearBullet.tick` moves by the previously stored `deltaMovement` on both sides; only the server then runs `BulletTickEvent`, steering, trajectory lookup/application, collision checks, and writes the next `deltaMovement`. The client never runs this trajectory branch.
- `BuiltinTrajectory` contains both per-distance position offsets (`WIGGLE_WORM`, `RING_WORM`, `OUROBOROS_WORM`, `MY_REFLECTION`) and velocity/rotation changes (`TINY_PLANET`, `HOOK_WORM`, `GRAVITY`). These are applied to the server's next movement vector, so the client cannot independently reproduce them from its current code.
- The current diff's `EntityVisualStateSync` only sends freeze-source and visual-layer IDs for `LivingEntity`; it does not touch entity coordinates, motion, or generic entity packets, so it is not a plausible cause of TearBullet movement correction.
- `AttackContext.trajectories` is copied into each bullet and serialized through `SynchedEntityData` as a comma-separated string. This synchronizes trajectory metadata, but client-side `TearBullet.tick` never consumes it because trajectory processing is server-gated.
- Git history identifies the architectural change most associated with the symptom: commit `fcb0b1b` moved movement to `move(getDeltaMovement())` before the server-only planning branch and removed synchronized `TRAVELED`/`VELOCITY` fields in favor of local `traveled`/`velocity`. Before that commit, trajectory calculation ran on both sides and the relevant state was in `SynchedEntityData`; after it, the client cannot replay trajectory state.
- Forge's `PlayMessages.SpawnEntity` serializes the entity's current `getDeltaMovement()` into the spawn packet. `BulletAttack` correctly initializes it to the straight launch velocity before spawning, so the client initially predicts straight movement; this is not a missing-initial-velocity failure.
- `TEAR_BULLET` uses `.updateInterval(2)`. Forge's `ServerEntity` only evaluates/ships standard tracking changes on that cadence unless entity data is dirty, which explains a correction becoming visible after a small number of frames rather than exactly at emission.
- `ServerEntity` emits relative position packets and emits an entity-motion packet when the tracked delta movement changes. Thus, after server-only trajectory planning first changes the next motion, the client receives a delayed authoritative position/motion correction and subsequently tends to look correct.
- No `BulletTickEvent` subscriber, visual-state packet, or current workspace diff calls `TearBullet.setPos`, `moveTo`, or `teleportTo`. Bullet bounce paths can deliberately replace velocity after a collision, but do not match a clean immediately-post-launch one-time jump.
- Design clarification: the source-level double buffer is correct (`move(d_t)`, then compute/store `d_t+1`). The missing guarantee is transport timing: `setDeltaMovement(d_t+1)` only changes server state; Forge sends it according to entity tracking cadence and ordinary network latency. Therefore the client moves by the most recently *received* `d_k`, not necessarily the immediately previous server plan `d_t`.
- With the current `.updateInterval(2)`, launch sequence is `S1: move d0, plan d1 (not necessarily sent); C1: move d0; S2: move d1, plan/send d2; C2: still may move d0`. The next position/motion update corrects that one-tick divergence. This is consistent with the intended simulation order but conflicts with the implicit requirement that `d_t+1` arrives before the client needs it.
- Perfect visual synchronization cannot be guaranteed with non-deterministic server-only trajectory/steering and sparse motion packets. It requires one of: client/server deterministic replay with identical inputs and sparse correction; authoritative snapshots rendered from a deliberate interpolation buffer; or motion updates whenever the plan changes (often every tick for curved trajectories). A one-tick movement delay alone does not remove that information/latency constraint.

## Ranked Hypotheses

1. **Most likely: the client predicts the launch vector while the server alone produces the next movement plan.** `BulletAttack` sends the spawn packet with `deltaMovement = v0`. On server tick 1, `TearBullet` moves by `v0`, then applies trajectory/steering and stores `v1`. The client does not execute that branch and moves by `v0` again. At the two-tick tracking update, Forge sends authoritative position/motion, correcting the client from `P0 + 2v0` toward `P0 + v0 + v1`. The apparently isolated jump is that first correction; the received motion then makes subsequent client movement much closer to the server.
2. **Trajectory algorithms magnify, but do not create, the synchronization design flaw.** Any non-zero `positionOffset`, `velocityOffset`, or rotation changes `v1`. `TINY_PLANET`, `GRAVITY`, and the offset-based trajectories can make the first correction conspicuous. `HOOK_WORM` may defer its first rotation until traveled distance crosses an integer segment, explaining an initially straight flight before the correction.
3. **No-trajectory case: server-only homing/control is the matching built-in cause.** `handleSteering()` runs every fourth tick only on the server. A homing or controllable bullet can therefore produce the same delayed correction with an empty trajectory map. Bounce is another deliberate server-only motion change but requires a hit.
4. **If a bullet has neither trajectory nor homing/control/bounce, current source does not contain a post-launch coordinate reset.** The spawn packet already carries initial motion, and no current `BulletTickEvent` handler or freeze-system change moves `TearBullet` by absolute coordinates. In that narrowed scenario, capture packet/tick logs before assigning blame; likely external event handling, an actually non-empty trajectory map, or observation of normal initial tracker interpolation rather than a server teleport.
